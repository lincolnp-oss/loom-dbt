# The jaffle shop, converted

This example is dbt's canonical tutorial project, the jaffle shop, after a Loom conversion. It exists to show the adoption loop run honestly on a project nobody designed for Loom: three of its five models converted to Loom-generated models, two deliberately did not, and the project ends in the hybrid state the adoption playbook treats as a first-class outcome rather than a failure to finish.

The end state, in one paragraph: the three staging models (`stg_customers`, `stg_orders`, `stg_payments`) are declared in `metadata/` and generated by Loom; the two marts (`customers`, `orders`) remain hand-written SQL exactly as upstream wrote them, and are registered in `local/registrations/` so the whole project is one inventory. The build is unchanged: `dbt build` reports PASS=28 before the conversion and PASS=28 after it, and the converted staging models produce row-for-row the same data as the hand-written originals (verified by comparing the two builds table by table; the only difference anywhere is the `__loaded_at` column the staging generator adds).

## Provenance

The project is vendored from [dbt-labs/jaffle_shop_duckdb](https://github.com/dbt-labs/jaffle_shop_duckdb) at commit `20cc904370818ceab08cf19f8fd196e9e81def88`, under its Apache-2.0 licence (see `UPSTREAM-LICENSE`). Carried over: `dbt_project.yml`, the models, the seeds, and the project's own documentation files. Not carried over: the upstream repository's platform and tooling files (devcontainer, Dockerfile, CI, editor configuration), which are about running the tutorial on dbt's platforms rather than about the project itself. Two files were adapted during the conversion, and both adaptations are explained below: `profiles.yml` (rewritten in the form the other examples use, with the target schema stated explicitly) and `dbt_project.yml` (one materialisation rule moved, nothing else).

## Run it

You need Python, Loom, and dbt with the DuckDB adapter:

```bash
python -m pip install loom-dbt dbt-duckdb
loom validate
loom generate --write
dbt seed
dbt build
```

`loom validate` reads the inventory (3 instances, 2 registrations) and reports it sound. `loom generate --write` writes the seven generated files: the three staging models and the generated sources document under `models/_generated/staging/`, and one properties document per staging model under `models/_generated/tests/`. Those outputs are not committed to this repository (the example's `.gitignore` excludes them); generating them is the first step of running the example, the same as in the quickstart.

One ordering note: seed before you build. The staging models read their inputs through a dbt source (see the binding decision below), and a `source()` reference creates no dependency edge to the seed that loads the table, so on a completely fresh database a bare `dbt build` can try to create the staging views before the seed tables exist. `dbt seed` first is the normal jaffle workflow in any case. After the build, two checks close the loop:

```bash
loom coverage
loom generate --check
```

Coverage reports all five project models inventoried (3 controlled, 2 registered), and the check confirms the generated files on disk are current against the metadata.

## How it was created

The conversion used loom-dbt 0.1.0 and followed the adoption playbook's order: convert first, register what stays hand-written second, and no model was swapped until its replacement was proven.

**Baseline.** The vendored project was built untouched: `dbt build`, PASS=28 (3 seeds, 5 models, 20 tests). That build's database file was kept as the equivalence baseline.

**Assessment.** After a `dbt parse` (convert calibrates its fit rules against a parse-produced manifest), `loom convert` reported: `0 ready to promote, 3 needs authoring, 2 not draftable`. For the three staging models it drafted authoring scaffolds: a pattern and one instance per model, with the transform left as a named authoring hole, because the staging models read seeds through `ref()` and a staging model must bind a dbt source, so convert would not guess the binding or the column mapping. For `customers` and `orders` it reported no fit and named the blocking signals; the next two sections quote and explain them.

**Completing the staging scaffolds.** Three decisions, all recorded in `metadata/instances/staging.yml`:

- *Binding.* Each staging instance binds its seed's relation with `inline_source` (source name `raw`, the table names `raw_customers`, `raw_orders`, `raw_payments`), so Loom generates the source declaration itself into `models/_generated/staging/sources.yml`. The schema in each binding is `main`: the schema the seeds materialise into under this project's profile, which is what the manifest records for each seed node. It is not the name of the seeds directory, and getting it wrong is the one error this conversion can make silently, so it is worth stating plainly.
- *Columns.* The mappings were authored from the hand-written SQL: identifier renames (`id` to `customer_id`, `user_id` to `customer_id`, and so on) and, for `stg_payments`, the cents-to-dollars conversion, which convert had already pre-placed in the draft as an expression item (`amount / 100 as amount`) because it appears in the model's final projection. Every projected output of each staging model is accounted for in its instance; an output with no mapping would be a named hole, not a silent drop.
- *Tests.* The staging models' existing tests (unique and not_null on the identifiers, accepted_values on `status` and `payment_method`) were carried into the instances as `generic_tests`, so they generate with the models into Loom's properties documents. With the tests homed there, the project's own `models/staging/schema.yml`, whose entire content was those tests, was retired in the swap; dbt allows one schema document per model, and the carried tests are the same declarations in the other home the promotion notes offer.

**Promotion, proof, swap.** The completed instances were merged into one instance set for the staging pattern and the pattern moved into `metadata/patterns/`, unchanged: promotion is file moves, no content edits. `loom validate` passed on the promoted set. `loom generate --write` then produced the generated staging alongside the hand-written originals, and Loom reported the shadowed state by name (a generated and a hand-written model sharing a name is a state dbt cannot parse, and the report says so and names the way out). The hand-written staging files were then removed, the project rebuilt from an empty database, and the result compared against the baseline: all five models identical on their shared columns, the generated staging models carrying the one additional generated column, `__loaded_at`. Only then was the swap left in place.

One configuration consequence of the swap is preserved deliberately. Upstream's `dbt_project.yml` made the staging layer views through a path-scoped rule over `models/staging/`; the generated staging lands under `models/_generated/staging/`, outside that path, so the rule moved with the files and now scopes the `_generated` staging directory. Without the move, the swap would have silently changed the staging layer from views to tables.

**Registration.** `loom register --write` drafted registrations for `customers` and `orders`, taking their descriptions from the project's own schema documentation; the owner fields were completed and `loom validate` confirmed the full inventory: 5 entries in 5 documents, coverage 5 of 5.

## What was converted, and why it fits

| Model | Binding | What the instance declares |
| --- | --- | --- |
| `stg_customers` | `raw.raw_customers` | `id` renamed to `customer_id`; `first_name`, `last_name` carried |
| `stg_orders` | `raw.raw_orders` | `id` to `order_id`, `user_id` to `customer_id`; `order_date`, `status` carried |
| `stg_payments` | `raw.raw_payments` | `id` to `payment_id`; `order_id`, `payment_method` carried; `amount / 100` as `amount` |

The staging layer is the shape the staging generator exists for: one source relation in, an explicit projection out (renames, casts, and simple per-column expressions), no joins, no aggregation, no business logic beyond the projection. Everything a staging model does is visible in its column list, so everything it does can be declared as a column list. That is the general rule this example demonstrates: conversion fit is about the shape of the transformation, not about the model's importance or size.

## What was not converted, and why

### `orders`

Convert's blocking signals for `orders`: aggregation (GROUP BY), a JOIN, 2 model dependencies, and the Jinja loop, named in the report itself: a `{% for payment_method in payment_methods %}` block is not something a column mapping can draft.

The loop is the substantive blocker, not a tooling gap. The model's column set is computed at build time from a list: one `<method>_amount` column per entry in `payment_methods`, produced by unrolling `sum(case when payment_method = ... then amount else 0 end)` once per entry. A Loom instance declares a fixed set of output columns, because a model's schema is its contract: it is what tests attach to, what coverage checks, and what downstream models rely on. A generator that manufactured columns from a list (or, worse, from the distinct values in a table) would make that contract a function of data or of a Jinja variable, changing silently when either changes, and unverifiable from the metadata alone. Dynamic column generation is therefore outside Loom's vocabulary by design, not by omission. `orders` is registered, its SQL is byte-identical to upstream, and its ten tests stay in `models/schema.yml` where upstream put them.

### `customers`

Convert's blocking signals for `customers`: aggregation (GROUP BY), a JOIN, 3 model dependencies.

`customers` is a multi-stage transformation wearing a single model's clothes. It pre-aggregates orders to customer grain (`customer_orders`: first order, most recent order, order count), pre-aggregates payments to customer grain through a join to orders (`customer_payments`: lifetime value), and then left-joins both onto the customer list, renaming as it goes. A Loom generator expresses one transformation stage in one statement; stages compose through the model graph, not through CTEs inside one model. Nothing in `customers` exceeds what Loom can express stage by stage (see the next section), but expressing it means decomposing it, and decomposition changes the project's model graph: two intermediate models appear that upstream never had. That is a remodelling decision, with real arguments on both sides (the intermediate grains become testable and reusable; the project also gains two models to own), and it belongs to the practitioner. Convert drafts only what it can prove fits the shape that is already there, so it does not draft decompositions. `customers` is registered, unchanged, with its three tests in `models/schema.yml`.

Registration is the designed end state for both models, not a consolation: registered models are in the inventory, searchable, coverage-checked, and counted, and convert withdraws them from its drafting pool so a later conversion pass works on what is actually left.

It is worth saying plainly that none of this is a defect in the original project, or in dbt. dbt deliberately offers practitioners several approaches to model design (plain SQL, composed CTEs, Jinja templating and macros, dynamic generation among them) and treats the choice between them as a matter of practitioner approach; the jaffle shop is a teaching project and demonstrates several of them on purpose. Loom's side of the bargain is narrower: it generates deterministically from metadata, so it can only stand behind a model whose complete definition exists at author time as a fixed, declared shape. Where a practitioner has used dbt's build-time machinery to decide what a model is (which columns it has, which stages compose it), deterministic generation is not applicable without crossing the author-time boundary: Loom would have to stop describing the practitioner's model and start making their build-time decisions for them. Models beyond that line are not lesser models. They keep the authorship dbt gives their practitioner, and Loom's role for them is the inventory, search and coverage they get by registration.

## If you remodelled them instead

The previous section gives the reasons in prose; this one shows the actual metadata, so the cost of the trade is concrete rather than rhetorical. Both remodels were built and verified against this example: the remodelled project's build passes in full, and `customers` and `orders` produce row-identical output to the hand-written originals on every shared column. Neither remodel is applied in this example; the hybrid state above is the conversion's result. What follows is what choosing otherwise looks like.

**`orders`: unroll the loop.** One gold instance replaces the registration. The Jinja loop becomes four enumerated measure expressions, written exactly as upstream's loop body writes them (including its `else 0`), plus the total:

```yaml
name: gold_marts
generator: gold
required_params:
- description
- owner
- input_models
- aggregation
```

```yaml
pattern: gold_marts
instances:
- name: orders
  params:
    description: One row per order with its payment totals, overall and per payment
      method, over the staging layer.
    owner: jaffle_shop
    skip_properties_document: true
    input_models:
    - stg_orders
    - stg_payments
    joins:
    - model: stg_payments
      on:
      - order_id
    aggregation:
      group_by:
      - order_id
      - customer_id
      - order_date
      - status
      measures:
      - column: amount
        expression: sum(case when payment_method = 'credit_card' then amount else 0 end)
        alias: credit_card_amount
      - column: amount
        expression: sum(case when payment_method = 'coupon' then amount else 0 end)
        alias: coupon_amount
      - column: amount
        expression: sum(case when payment_method = 'bank_transfer' then amount else 0 end)
        alias: bank_transfer_amount
      - column: amount
        expression: sum(case when payment_method = 'gift_card' then amount else 0 end)
        alias: gift_card_amount
      - column: amount
        expression: sum(amount)
        alias: amount
- name: customer_orders
  params:
    description: Per-customer order aggregates over the staging orders model.
    owner: jaffle_shop
    input_models:
    - stg_orders
    aggregation:
      group_by:
      - customer_id
      measures:
      - column: order_date
        expression: min(order_date)
        alias: first_order
      - column: order_date
        expression: max(order_date)
        alias: most_recent_order
      - column: order_id
        expression: count(order_id)
        alias: number_of_orders
- name: customer_payments
  params:
    description: Per-customer payment totals, attributed through the staging orders
      model.
    owner: jaffle_shop
    input_models:
    - stg_payments
    - stg_orders
    joins:
    - model: stg_orders
      on:
      - order_id
    aggregation:
      group_by:
      - expression: stg_orders.customer_id
        alias: customer_id
      measures:
      - column: amount
        expression: sum(stg_payments.amount)
        alias: total_amount
```

Two properties of this shape are worth noticing. The measures' expressions are upstream's own SQL, so the aggregation's meaning does not move; what moves is where the payment-method list lives, from a Jinja variable to the instance, where adding a method is a reviewed schema change. And the generated model carries gold's `__loaded_at` column and gold's emitted `not_null` tests on its measures: on data where an order can have no payments, those tests fail the build rather than pass a NULL total silently, which is gold's documented behaviour for unmatched rows (the metadata reference's "Gold joins and measure tests" section gives the declaration that softens them, if NULL is the semantics you want). One genuine semantic residue: an order with no payments at all reads 0 in each per-method column under the remodel where upstream reads NULL; its total reads NULL under both.

**`customers`: promote the CTEs to models.** The two pre-aggregations become gold models in their own right, in the same instance set:

(the customer_orders and customer_payments instances from the same file above)

and the final assembly becomes a view instance that joins the three and applies the one rename:

```yaml
name: assembly_view
generator: view
required_params:
- description
- owner
- input_models
- select_columns
```

```yaml
pattern: assembly_view
instances:
- name: customers
  params:
    description: One row per customer with their order history aggregates and lifetime
      value, assembled from the staging customers model and the two per-customer
      aggregates.
    owner: jaffle_shop
    skip_properties_document: true
    input_models:
    - stg_customers
    - customer_orders
    - customer_payments
    joins:
    - model: customer_orders
      on:
      - customer_id
    - model: customer_payments
      on:
      - customer_id
    select_columns:
    - source: stg_customers.customer_id
      alias: customer_id
    - source: stg_customers.first_name
      alias: first_name
    - source: stg_customers.last_name
      alias: last_name
    - source: customer_orders.first_order
      alias: first_order
    - source: customer_orders.most_recent_order
      alias: most_recent_order
    - source: customer_orders.number_of_orders
      alias: number_of_orders
    - source: customer_payments.total_amount
      alias: customer_lifetime_value
```

The graph is the price and the prize in one move: `customer_orders` and `customer_payments` are now models a practitioner can test, search and reuse, where upstream they were intermediate steps inside one model's CTEs. The assembly's generator is `view`, so remodelled `customers` materialises as a view where upstream's is a table; the data is identical, and a team that cares about the materialisation more than the projection control would choose differently or keep the registration. Both remodelled marts declare `skip_properties_document`, because their descriptions and tests already live in the project's own `models/schema.yml`, and dbt allows a model exactly one schema document: the practitioner's document stays the home, and Loom watches that it keeps a description.

**The swap itself** is the same discipline as the staging conversion: delete the two registrations, add the two pattern files and two instance files above, run `loom validate` and `loom generate --write`, remove the hand-written SQL (generation refuses to overwrite it until you do), seed, and build. Nothing else in the project changes: the staging layer, the seeds, and the marts' own tests are untouched, and the build's test count rises only by the tests the new generated models bring with them.

**In general:** convert's drafting is deliberately conservative. It drafts a model when the model's existing shape provably matches a generator's contract (staging above), scaffolds an authoring draft when the layer is clear but the transform must be written by a person (also staging above, because of the seed binding), and declines when the shape crosses stages or manufactures its own schema. Everything it declines can still join the inventory by registration, and most can be remodelled into authored metadata by a person who decides the new shape is worth having. The line the tool holds is that it will not make that decision silently on the project's behalf.

## The directory, briefly

- `metadata/patterns/staging_pattern.yml` and `metadata/instances/staging.yml`: the staging layer's declaration, pattern and instances together.
- `local/registrations/`: the two marts' registrations.
- `models/`: the hand-written marts and their schema and documentation files, as upstream wrote them. Everything under `models/_generated/` is produced by `loom generate` and is not committed.
- `seeds/`: the raw data, as upstream ships it; the staging models bind the relations these seeds load.
- `dbt_project.yml`, `profiles.yml`: upstream's project configuration with the two adaptations described under Provenance.
