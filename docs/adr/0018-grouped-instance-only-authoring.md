# ADR 0018: Use grouped named instances as the only generated-model authoring format

Status: accepted. This record states the complete current authoring decision in current terminology (ADR 0023), including the named-definition and staging column-macro decisions.

## Context

Loom's authoring surface grew three overlapping forms: combined pattern families (defaults and instances in one file), standalone single-model records, and named definitions with separate instance files. Multiple ways to author the same generated model multiply validation paths, provenance shapes and documentation, and Loom is greenfield - it does not need to maintain them in parallel. Practitioners also need one reusable definition that many instance sets can reference, and a way to apply a dbt macro to a staging column without writing SQL in metadata - project-authored macros first, and, as the owner's validation of a real project showed, package macros above all: on the validation project 666 of 672 manifest macros were package-declared, so a project-only rule excluded the macros practitioners actually use.

## Decision

**One authoring format.** Generated models are authored only as *instance sets* against *named pattern definitions*:

- A **pattern definition** lives at `metadata/patterns/<name>.yml` (the file stem must equal `name`), with a `name` matching the file stem, a `generator`, optional `defaults`, and optional `required_params`. It names the behaviour; it is an authoring input, not an inventory entry, and unused definitions are still validated.
- An **instance set** lives under `metadata/instances/`, with a `pattern` reference and a non-empty `instances` list of `{name, params}`. A set of one is the normal way to declare a single model. Each instance expands to a record that is validated by its generator's contract and takes part individually in duplicate-name detection, relationship checks, inventory search, manifest coverage and generation, with its own inventory path (`metadata/instances/<file>.yml#instances[<name>]`).

**Merge and identity rules.** A field may appear in a definition's `defaults` or an instance's `params`, never both - Loom has no override precedence and rejects the overlap. The standing exception is the envelope keys (ADR 0032): keys generation consumes rather than a renderer - `output_subpath`, `contract_enforced`, `skip_properties_document` - may appear in both, with the instance winning, which is the one mechanism that can express "for this pattern, except this one model". A definition's identity fields (`generator`, `name`) cannot be defaulted. `required_params` lists fields every instance must state explicitly; each must be a non-identity parameter of the generator and must not also carry a default. Two declaration families are instance-only by construction and are barred from `defaults`: `unit_tests` and `generic_tests` (ADR 0029) - both name one model's fixtures or declarations. Values are copied verbatim - no templating, Jinja, interpolation or expression evaluation in metadata. Unknown fields are rejected in both document types, and documents outside their directories are rejected. The documents originally also carried a `document_type` field naming their kind in-band; it was dropped before release because the paths already discriminate - definitions, instance sets and registrations each live in their own directory, and convert's drafts are path-separated the same way (`local/drafts/patterns/`, `local/drafts/instances/`; the flat `local/drafts/<model>.yml` files are convert-internal draft records, not practitioner metadata). Classification is by path alone: each role validates its own required shape. Loom documents carry no format version: no writer emits one and no loader reads one, so there is nothing to default, check or migrate - the release-hygiene rule that replaced versioning is recorded in the architecture document.

**Retired forms are errors, not aliases.** Combined `pattern_family` documents, standalone generated-model records and standalone instance files are rejected with migration guidance rather than silently interpreted. Hand-written models are not authored this way at all: they join the inventory through descriptive *model registrations* under `local/registrations/`, whose schema is a registration format, not a generation format.

**Provenance.** Generated output headers record the pattern definition's identity (`name`, `path`, and a SHA-256 of the whole definition document), and the generated-file hash covers the expanded record plus that identity - any definition edit, even one that leaves expanded values unchanged, changes generated provenance and is caught by `loom generate --check`.

**Staging column macros - tiered acceptance.** A staging `columns` mapping may name a dbt macro:

```yaml
columns:
  - {source: subtotal, alias: subtotal, macro: cents_to_dollars}
  - {source: tax, alias: tax_dollars, macro: cents_to_dollars, macro_args: [4, true, "USD"]}
  - {source: created_at, alias: creation_day, macro: dbt.date_trunc, macro_column_param: 2, macro_args: ["day"]}
```

which generates `{{ cents_to_dollars('subtotal') }} as subtotal` - the raw column is passed as a quoted column name, and `alias` remains the output alias. The reference takes exactly two forms, the two forms dbt itself writes: a **bare name** is a project macro, and a **namespaced `package.name`** (exactly one dot, both segments safe identifiers) is a package macro. The name must not be a reserved dbt context/Jinja name. The tiers differ in who verifies the reference, because the surfaces hold different evidence:

- A **project macro** is verified where it is authored: validation requires a `{% macro %}` block of that name in a `.sql` file under the project's macro-paths, and its absence is a hard error.
- A **package macro** cannot be verified by `loom validate`, which holds no manifest: validation warns "unverified package macro" and never blocks. The manifest-holding surfaces verify it - `loom convert` drafts only macro calls verified against the manifest's macro index (existence, then arity against the signature's ordered arguments, defaults counted), and `loom check` verifies generated instances' package macros against the manifest as errors. `loom generate` stays manifest-free and renders the invocation as declared.
- **`macro_column_param`** names which signature parameter the source column fills (a positive integer, default the first); the renderer assembles the arguments in signature order, with `macro_args` supplying the remaining literals. This is what makes a non-column-first signature such as `dbt.date_trunc(datepart, date)` expressible. An explicit position of 1 is the slot itself - omitting the parameter and pinning position 1 assemble the identical call, pinned by golden tests. The invocation is emitted as a plain Jinja expression call (`{{ macro(...) }}`): the slot's first rendering used the `{% call %}` block form, which dbt rejects for ordinary macros ("two values for the special caller argument"), and the emitted form was corrected before release; the argument assembly described here never changed, and a runtime test now compiles macro-slot models under dbt.

A raw source column may appear in several mappings when each is a distinct transformation; at most one plain projection per raw column, and the same macro + args (and column position, where `macro_column_param` is declared) may not be applied to it twice; `alias` values must remain unique. `macro_args` (1–8 items, requires `macro`) are fixed literals only - integers, booleans, or strings of at most 200 characters from a safe character set; floats, nulls, mappings, lists and quotes are rejected, so no escaping is needed and no raw SQL or Jinja can be emitted - the literal-argument rules are unchanged by the tiers, which is what keeps the slot's no-raw-SQL property. Loom does not execute or inspect the macro body; its SQL is produced at dbt compile/run time and its correctness is the project's responsibility. Omitting `macro` keeps the original `<source> as <alias>` projection byte-for-byte.

The road taken, in short: the slot originally accepted project macros only, because they were the only references Loom could verify from the project tree alone. Package macros are by far the more common case, and the manifest - already a prerequisite of the verifying commands - carries their signatures; tiering the acceptance by surface evidence removed the exclusion without weakening any surface's guarantee.

## Consequences

There is exactly one generated-model authoring path to validate, document and search; pattern definitions are reusable across instance sets and projects without copying defaults. The cost is deliberate: small projects write two files (definition + instance set) where a single record might seem enough - accepted, because the definition is where reuse and project conventions live, and the first-project example shows the pair is small. Behaviour contracts per generator are unchanged by this decision; they live in the generator contracts and the architecture document.
