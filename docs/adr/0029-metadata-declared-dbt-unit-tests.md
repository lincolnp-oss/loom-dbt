# ADR 0029: Tests - Loom originates paradigm guarantees, hosts practitioner declarations

Status: Accepted

## Context

Tests are where Loom's authorship boundary is easiest to get wrong. A generator knows its paradigm's structural guarantees and can prove them mechanically; it knows nothing about a project's business expectations, and a tool that manufactures those teaches practitioners to trust assertions nobody made. But dbt gives some declarations nowhere else to live: a model's schema document carries exactly one description of its tests, and Loom generates that document - so practitioner declarations that belong in it must pass through Loom's metadata or be overwritten by regeneration. And some declarations only Loom can check, because only Loom holds the inventory they must agree with.

An earlier decision also excluded dbt unit fixtures from the first build: Loom would not manufacture business expectations for project-authored macros, and a fixture must not imply it proves a snapshot's lifecycle. It set a three-part reconsideration gate - an explicit generator contract, tests against the supported dbt version, and proof that incremental and snapshot fixtures do not depend on pre-existing warehouse state. The conditions for meeting that gate now exist: the generator contracts give every parameter a checked home, and the output-column resolver derives every generator's output columns from its renderer's SELECT construction, so fixture column names can be validated against renderer truth rather than guessed.

## Decision

**The tests principle.** *Loom originates only paradigm-guarantee tests; it hosts practitioner declarations where it must (carriage - forced by dbt's single-description rule) or where only it can check them (instance-level declarations validated against the inventory); it does not originate practitioner content.* The three clauses have one home each: origination is ADR 0015's contract-derived data tests; carriage and inventory-checked declaration are this record.

**Carriage: `generic_tests`.** Practitioner-declared generic (data) tests are hosted as an optional common parameter on every generator contract - staging, bronze and SCD2 included. The declaration is copied verbatim: test name, attached column and kwargs are carried unexamined, test names are never checked against a registry, and the parameter is barred from pattern `defaults` (a declaration names one model's tests). Exact duplicates of a declaration are a validation error; differing kwargs stay legal. An underivable kwarg arrives as a `__TODO__` sentinel the validator rejects by name, so a scaffolded declaration cannot slip through unfilled. Generation emits carriage centrally through the generate plan, in the same properties document as the generator-derived tests; a model whose only tests are carried still gets its document, and a declared column missing from the properties entry gains a stub entry rather than dropping the test. Carried duplicates of generator-derived tests are emitted as declared - `loom check` warns on the duplication, and warns when a declaration is not attested by the manifest (`--strict` makes the attestation warning a failure). Convert drafts `generic_tests` for the tests a project already declares on a model, copying them into the draft's declared interface; a test declared on a *different* model (the `relationships` pattern) drafts onto the declaring model's instance. `loom create-new data-test <model>` prints the snippet: the metadata form for a generated model, the dbt-YAML fragment for a hand-written one; `--test` is required, because Loom never invents the test being declared.

**Inventory-checked declaration: `unit_tests`.** Practitioners declare dbt unit tests per instance in metadata, with the optional `unit_tests` parameter on every generator except `scd2_dimension`. For a source-fed generator (`staging`, `bronze`) the declaration's `given` input names the model's own source table instead of an inventory model, validation checks it against the instance's declared source, and generation renders it in dbt's `source('<name>', '<table>')` form; every other generator's `given` inputs name inventory models and render as `ref()`. The declaration is validated by the generator contract (top-level kind) plus a dedicated nested validator: names are project-unique snake_case; `given` inputs must be the model's declared upstreams; row columns are subset-checked wherever output columns are derivable; `overrides` is restricted to `overrides.macros.is_incremental`; fixtures are `dict`/`csv` only - no `format: sql`, no fixture files. Generation emits one central, generator-agnostic document per model to `models/_generated/tests[/<subpath>]/unit_<model>.yml` through the existing generation plan. `loom create-new unit-test <model>` prints the authoring snippet in the form the model needs - the metadata snippet for a generated (controlled) model, the dbt-YAML form for a hand-written one - and the metadata snippet's rows carry a `"__TODO__"` sentinel the validator rejects, so scaffolding never produces a hollow generated file.

The gate on unit tests is discharged as follows. *Explicit generator contract:* the parameter and validator above. *Tests against the supported dbt version:* a runtime integration proof (DuckDB) exercises generated dimension, persistent-hub, staging and bronze unit tests end to end; dbt >= 1.8 becomes a **conditional** floor - it binds only projects that declare `unit_tests`, and `generate` warns (never fails) when the project's existing manifest records an older `dbt_version`; dbt's own unit tests accept partial-column `dict`/`csv` fixtures, which is what makes models stamped with a run-time `__loaded_at` testable at all - the expected rows simply omit the stamp. *State-independence:* a fixture proves a single-load transformation, never a lifecycle - `scd2_dimension` is excluded (the model under test is a snapshot), and a persistent hub's tests must each declare `overrides.macros.is_incremental` so the fixture states which load it models.

## Consequences

- Staging, bronze and satellite are covered. The earlier staging/bronze exclusion rested on a reason that described the emitter - given inputs were rendered only as `ref()` of inventory models - not a dbt limit: on the jaffle validation fixture a staging model is unit-tested practitioner-side by mocking `source('ecom', 'raw_stores')`, macro transform included, passing `dbt build`, and that evidence displaced the exclusion. Satellite's absence from the contracts was a wiring gap, since closed: its given input is its inventory input model, in ref form, like the other Data Vault generators. Only `scd2_dimension` stays excluded, for dbt's own reason (unit tests target models; a snapshot is not a model). Links are supported for unit tests with a documented caveat - the link guard runs inside the link's SQL, so negative scenarios fail the run instead of asserting and are not expressible as link unit tests.
- `unit_tests` and `generic_tests` are instance-only: pattern `defaults` may not define either (fixtures and declarations name one model's upstreams, tests and expected rows). Both are stored in the instance's `params` and flattened to the expanded record's top level on expansion.
- The `unit_test_identity` field from the earlier proposal remains rejected; nothing about it is resurrected.
- Deleting a model's whole `unit_tests` block leaves a stale `unit_<model>.yml` behind - the same known stale-YAML gap as the data-test documents, to be fixed for both together or neither.
